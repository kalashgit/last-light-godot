## Architecture diagnosis

1. `draw_icon(recipe, variant)` has 19 branches made from fixed native64 primitives. Native drawing is a sound baseline, but object geometry is hard-coded and has no semantic parts, explicit depth/facets, masks or attachment graph.
2. The `material` and `brief` fields never influence rendering. A single multiplicative five-tone ramp shades plastic, fabric, leather, organic and painted metal alike; steel and wood have fixed shared swatches. There is no per-material reflection, roughness, thickness or wear model.
3. Lighting is manually approximated in individual polygons. There are no common plane normals, contact/crease occlusion rules or assembly-based shading constraints. A bright line is often used as the entire depth cue.
4. Item identity partly depends on ID substrings (`pear`, `ball`, `pipe`, `phillips`). Pipe/adjustable wrenches and backpack/tool bag share nearly identical geometry despite different construction requirements.
5. Variants beyond zero mostly do nothing; six archetypes receive a tiny deterministic scratch. Seeds do not generate meaningful independently designed objects. Variants cannot be counted as unique objects.
6. Recipe validation lacks construction parts, source/provenance requirements, camera/light contracts, view/state schema and recipe versions. IDs are unique on input, but output paths use only family plus last dotted ID segment, allowing path collisions for different IDs.
7. Resume accepts any existing 64×64 RGBA file without validating content hash, recipe/generator fingerprint, alpha integrity or semantic match. Corrupted files are logged rather than recovered. PNG writes are not atomic.
8. Input recipes and the per-job `exported` metadata list are retained for the full run. Contact-sheet pixels are bounded, but overall metadata memory is O(total recipes + jobs). JSONL output alone does not make the factory bounded-memory.
9. Re-running the same range opens manifests/errors with `w`, replacing prior range evidence. No immutable attempt history, job fingerprint, protected approval state or per-item rework trail exists.
10. V3 correctly calls its output draft and never claims visual approval. Its status must remain independent of the successful technical execution.
